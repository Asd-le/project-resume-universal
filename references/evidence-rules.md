# 证据规则（通用版）

本文件是 `project-resume-universal` 的判定基准。不确定一条结论该标什么等级时，回到这里。

---

## 一、四级定义

| 等级 | 定义 | 证据要求 | 能否写进简历 |
|---|---|---|---|
| `[CONFIRMED]` | 仓库内材料可直接证明 | 文件路径（可含行号）/ 配置键 / SQL 片段 / commit hash / 日志片段 | ✅ 事实陈述 |
| `[USER_PROVIDED]` | 用户本轮明确回答 | 记录回答要点 | ✅ 事实陈述 |
| `[INFERRED]` | 由结构合理推断，无直接证据 | 列出推断依据与不确定性 | ⚠️ 只能写「疑似/可能」 |
| `[USER_REQUIRED]` | 必须用户回答 | 给出问题与「为什么无法从代码判断」 | ❌ 禁止写入正文 |

---

## 二、按结论类型的默认等级

| 结论类型 | 默认等级 | 升级条件 |
|---|---|---|
| 项目使用了技术 X | `[CONFIRMED]` | 依赖清单 + 配置 + 代码使用痕迹，证据越多越强 |
| 技术 X 在生产启用 | `[INFERRED]` | 生产 profile/环境配置存在对应项，或有线上相关 commit |
| 用户参与模块 M | `[CONFIRMED]` | Git 有该作者对该模块的提交（给出次数与示例 commit） |
| 用户**负责**模块 M | `[USER_REQUIRED]` | 用户明确承认；或该模块由本人从 0 到 1 新增 + 长期维护 |
| 用户主导架构设计 | `[USER_REQUIRED]` | **Git 无法证明**，只有用户能确认 |
| 机制解决了线上问题 P | `[USER_REQUIRED]` | commit message 明确描述该问题，或用户确认 |
| 性能/容量数字 | `[USER_REQUIRED]` | 用户提供 / 文档 / 监控配置 / benchmark / 日志（须贴出处） |
| 项目规模（文件数/接口数/表数/提交数/代码行） | `[CONFIRMED]` | 采集器输出可直接支撑 |
| 复杂度（并发/一致性/跨库/跨端） | `[INFERRED]` | 存在具体机制（锁、事务边界、分片、ACK、幂等表）可升级 |

**例外**：`information_schema.TABLE_ROWS`、`COUNT(*)`、构建产物体积、依赖数量等**可重复测量**的数字属于 `[CONFIRMED]`，但必须注明是**估算值**还是**精确值**。

## 三、强证据 vs 弱证据

**强证据（可支撑 CONFIRMED）**
- 具体类/函数/组件的实现（贴关键片段）
- 配置文件的真实键值（脱敏后）
- Schema/迁移脚本（建表、加索引、改字段）
- commit hash + message + 变更文件
- 结构化运行期产物：日志配置、线程池/连接池参数、MQ 队列声明、监控规则
- 线上实测（数据库计数、访问日志聚合、错误日志分类）

**弱证据（只能支撑 INFERRED）**
- 只有依赖坐标，无使用痕迹
- 只有目录/类名符合某模式（如包名叫 `sharding` 但无分片配置）
- 被注释掉的代码、`TODO`
- 与业务无关的通用工具代码
- `scope=test`、`devDependencies` 中的依赖（不代表生产能力）

## 四、跨栈通用反例（每种项目都会踩）

### 反例 1 · 把「依赖存在」写成「生产在用」
```
❌ 使用 Kafka 构建高吞吐消息体系
✅ [INFERRED] 依赖中存在 kafka 客户端，但配置/代码无使用痕迹（列入待确认）
```

### 反例 2 · 把「项目用了」写成「我设计了」
```
❌ 我设计了整套微服务架构
✅ [CONFIRMED] 用户在该仓库有 N 次提交，涉及这些模块
✅ [USER_REQUIRED] 架构方案是否由本人设计？
```

### 反例 3 · 把「团队成果」写成「个人成果」
```
❌ 主导 9 家支付渠道接入
✅ [CONFIRMED] 本人实现 A/B/C 渠道（提交 X，文件 Y）；D/E/F 渠道由团队成员实现（提交 Z）
```
> 归属必须逐个核到 commit author；**这不是削弱经历，而是让经历经得起追问。**

### 反例 4 · 把「估算值」当「精确值」
```
❌ 最大分表 1,856 万行（精确统计）
✅ 最大分表：information_schema 估算 18,564,212 行；精确 COUNT 15,136,018 行
```

### 反例 5 · 把「配置里写的」当「实际生效的」
```
❌ 服务器配置 800 线程
✅ 基础配置写 800，但 profile include 的 druid 配置写 200 → 实际生效 200（需核对覆盖链）
```

### 反例 6 · 把「人工流程」说成「我做了系统」
```
❌ 我做了自动对账系统
✅ 我负责 A 渠道的销账链路与日终人工对账；B/C 渠道的对账文件下载由团队同学实现；
   代码里没有程序化自动比对（selectByPayOrderNo 定义后无调用点）
```

## 五、`08-evidence.json` 规范（踩过坑的硬约束）

1. **路径基准 = 仓库根**。写 `src/main/java/...` 全路径；不要写裸 `framework/...`（换项目即失效、无法机读校验）。
2. **`type=commit` 必须是 commit hash**；人类可读说明放 `note` 字段。
3. **`category` 只用枚举值**：`tech-stack | architecture | business | contribution | highlight | metric | quality | career`（新增值先在此登记）。
4. **`level` 只用四级枚举**。
5. **不得有重复 `id`**；`claims` 与 `pendingQuestions` 编号各自独立。
6. **`pendingQuestions[].status`** 取 `OPEN | RESOLVED`；已确认的移出或置 `RESOLVED` 并保留归档条目。
7. 交付前**必须校验 JSON 合法性**（`ConvertFrom-Json` 或 `JSON.parse`），并**逐条抽样核对 `ref` 路径存在**。
8. **数字要与证据文件一致**：JSON 里的统计口径必须能在 `evidence/*` 找到出处；否则标注 `[USER_REQUIRED]`。

## 六、写进简历前的自检清单

对每一句要入简历的话，逐条自问：

- [ ] 等级是 `CONFIRMED` 或 `USER_PROVIDED` 吗？
- [ ] 我能指出具体文件/配置/commit/日志吗？
- [ ] 句中每个数字都有来源，且注明估算/精确吗？
- [ ] 有没有把团队成果写成个人成果？
- [ ] 有没有把「参与」写成「负责/主导/设计」？
- [ ] 面试官追问「为什么这样设计」时，代码里有能支撑的答案吗？
- [ ] 这句话是否**只对某一种栈成立**？（跨栈项目常见：把后端结论写进前端版本）

任一项答不上来 → 降级表述或移入确认清单。
